# 知识工坊：大批量资料的少分窗生成方案

> 状态：大窗口分窗、生成前预览、按窗口出题、答案与审核拆批、断点恢复均已接入；按用户要求不做真实模型验收
> 更新：2026-09-23
> 范围：先解决资料一次性截断、有效文本覆盖不足的问题；本轮另补充大题数拆批与窗口均衡，答案和审核的质量策略重构仍另行设计。

## 1. 结论与目标

采用**大窗口优先、最少必要分窗**，不预设每窗只有 12k～20k token，也不按资料份数或片段数推断窗口数。以用户提出的 Codex 界面 258k token 为初始参考上限：如果知识工坊实际选用的模型和供应商允许，单次模型请求的**完整输入**目标上限为 `258,000 × 70% = 180,600 token`。资料之外的系统提示词、JSON Schema、请求参数和序列化开销都占用这 180,600 token，须从中扣除。

258k 是参考值，不代表知识工坊所有可选模型都具有 258k 上下文。实际容量更小时，以实际容量为准；容量更大时，初版仍以约 180.6k 为用户期望的单次输入上限，后续可开放配置。上下文还包含输出及某些模型的推理 token，因此 70% 是输入目标而非“把上下文填到 70% 就必然成功”的保证。[OpenAI 对上下文计量的说明](https://developers.openai.com/api/docs/guides/conversation-state)。

预期效果：能在一窗中完整容纳的资料只发一窗；确实放不下时才拆成两窗或更多窗。此前提到的“7 份资料、286 个片段、预计 9 窗”是采用过小窗口预算的示意，**不是**依据这批资料实际 token 量测得的结果。

## 2. 当前实现与必须解除的限制

实施前代码按数据库顺序从所选资料中取片段，累计到 `MAX_CONTEXT_CHARS = 72_000` 字符即停止，最后一个片段也可能被截断。现已取消该字符截断；服务把全部可用片段交给窗口规划器，规划器以完整请求的估算 token 打包。题目规划按窗口调用，汇总去重后进入答案生成阶段。相关代码见 `src/main/knowledge-studio/knowledge-studio-service.ts` 与 `knowledge-model-provider.ts`。

原来的固定 `maxInputTokens: 80_000` 已改为按任务保存的模型容量、模型自身最大输出元数据与推理预留动态计算。知识工坊不再设置应用层输出 token 上限或温度参数，模型仍受自身能力和剩余上下文限制。规划器与网关共享同一套 ASCII/非 ASCII 文本估算口径，并计入最终组合的系统提示词、Schema 约束与用户 JSON。供应商返回的实际用量仍是最终依据。

默认请求超时为 120 秒，当前设置范围为 10～300 秒。较大的输入可能增加首字等待、总耗时和供应商超时风险；实施时须同时核对超时、流式响应与失败恢复，不能把“上下文装得下”误认为“请求一定能完成”。

生成实录展示每次独立模型调用实际纳入的资料正文字符数、网关最终组装的可见输入文本字符数、调用前估算 token，以及模型返回的实际输入/输出 token；实际输入计入缓存输入。失败且供应商未返回用量时标记“未返回”，不记作 0。这些数据用于校准字符与 token 的关系。

## 3. 容量与 token 预算

在生成任务创建时确定并保存以下值，重试和继续任务时沿用同一模型及预算快照：

- `C_model`：所选模型实际上下文容量，优先来自运行时模型元数据；不能从 Codex 聊天界面的 258k 直接推断。
- `L_provider`：供应商或所用接口若另有明确的单次输入上限，记录该上限。
- `R_output_reasoning`：模型自身最大输出元数据与推理空间所需的预留，不是应用层施加的输出上限。预留的 30% 是起点；如果所选模型/思考程度需要更多空间，则降低输入预算。
- `O_request`：对**实际将发送的完整请求**估算出的非资料 token，包括系统提示词、输出协议/Schema、目标岗位、难度、题数和 JSON 包装。

初版计算原则：

```text
B_full_input = min(
  floor(0.70 × min(C_model, 258_000)),
  L_provider（如果存在）,
  C_model - R_output_reasoning
)
B_sources = B_full_input - O_request
```

若 `C_model ≥ 258k`、供应商没有更低的输入限制、输出及推理预留也不要求进一步缩减，则 `B_full_input ≈ 180,600 token`。例如完整请求中非资料部分估计为 6,000 token 时，资料净预算约为 174,600 token；6,000 只是说明计算方法的例子，不是固定开销。

token 统计优先使用与所选模型匹配的 tokenizer 或供应商计数能力；不可用时用保守估算，并在界面明确标为“预计”。最终应在**请求完成组装后**再次测算整个 system + user 输入，而非只累加片段内容。记录估算值与供应商返回的实际用量，逐步校准估算误差。

若模型容量无法核实，不把 258k 当作事实直接使用：先显示“容量待确认”，从模型元数据、供应商配置或明确的用户配置取得上限，再启用大窗口。不能悄悄退回固定 72,000 字符截断。

## 4. 分窗算法与资料覆盖

1. 读取所选资料的**全部**可用片段，保留资料 ID、片段 ID、标题、章节顺序与原文。先统计总预计 token，再计算理论最少窗口数；片段数仅用于展示，不参与窗口数公式。
2. 以 `B_sources` 为每窗净资料预算，优先沿资料及章节顺序装入完整片段。先确定最少可行窗口数，再尽量在章节边界均衡各窗，避免前窗过满、末窗过小。
3. 单个片段超过预算时才在段落/句子边界继续拆分；保留父片段 ID 与子范围，必要的边界重叠应小且可计量。不得直接 `slice` 后丢弃尾部。
4. 为每个片段记录 `includedWindowIds`。运行前校验所有待处理片段都被覆盖；重复携带的边界文本单独计量。任何因格式错误、解析失败或用户取消而未进入窗口的内容都必须显式列出原因。
5. 一个窗口足够时保持单次规划；多窗口时分别产出可追溯的局部题目候选，再对候选进行跨窗口去重与总题数选择。每题的证据 ID 必须仍能指回原始资料。此处只增加分窗必需的汇总步骤，不在本方案中重设计逐题答案和最终审核。

例如，在资料净预算约 174k token 的条件下，若全部资料共约 300k token，预估约两窗；若共约 500k token，预估约三窗。**286 个片段本身无法说明是两窗、三窗还是更多窗。**

## 5. 超限、超时与恢复

- 本地预检或供应商明确报告上下文超限：只重排失败窗口，缩小其预算后重试；记录原预算、错误与新预算，不重新处理已成功窗口。
- 请求超时：先区分客户端绝对超时、供应商超时和网络故障；保留失败窗口与调用诊断。允许延长合理超时或使用流式/后台等待。连续超时后可缩小该窗口，但不能把所有超时一律归因于“资料太长”。
- 供应商不可用、鉴权和限流：按错误类型处理，不通过无意义的资料分窗来掩盖问题。
- 任一窗口失败时任务可局部重试；成功窗口的候选与用量记录应持久化，避免整批重新付费和生成不一致。

## 6. 界面与诊断信息

开始生成前显示：所选资料数、可用/异常片段数、全文预计 token、选定模型的容量来源、70% 完整输入预算、扣除提示词/Schema 后的资料净预算、预计窗口数与预计覆盖率。若容量来自估算或用户配置，明确标注，不伪装成供应商保证。

生成实录按窗口展示：窗口编号、所含资料/片段范围、请求预计与实际输入 token、非资料开销、输出 token、耗时、模型/思考程度、错误类型，以及该窗口产生的候选数。可展开完整 system、Schema 与 user 请求，但默认折叠长原文。完成后展示实际覆盖片段数、未覆盖原因、跨窗口去重前后题数。

## 7. 验收标准

- 在相同模型容量和同一批资料下，窗口数由完整请求的 token 预算决定；能一窗装下就只生成一窗，不因“7 份”或“286 个片段”人为分成 9 窗。
- 选中资料不会被 72,000 字符上限静默截断；每个片段均被处理或有明确的未处理原因。
- 任何发送到模型的完整输入不超过本任务计算并展示的预算；应用层 80,000 token 上限不会与界面宣称的约 180.6k 预算相矛盾。
- 覆盖单窗、多窗、超长单片段、中英文混合估算、模型容量不足、上下文超限、超时后局部重试和取消恢复的测试。
- 对真实资料做一次对照：记录总预计/实际 token、实际窗口数、覆盖率、调用成功率、耗时与题目重复率；以数据决定是否调整 70% 比例，而不是先固定缩回小窗口。

## 8. 实施顺序

1. 暴露并记录所选模型的实际容量，统一完整请求 token 计数与动态预算；先让界面预览结果可信。
2. 用可追溯的窗口打包替换 72,000 字符截断，并同步调整 80,000 token 本地上限。
3. 接入多窗规划、候选汇总、窗口级检查点与局部重试。
4. 完成上述验收测试，再用真实资料比较单窗/多窗的质量、速度、成本和失败率。

## 9. 本轮实施记录与待验证项

- 运行时模型列表现在暴露上下文容量和最大输出元数据；任务创建时固定模型与容量快照。容量未知会明确拒绝大窗口生成，而不是假定具有 258k 上下文。旧任务重试时会补固定快照。
- 预览调用和实际生成共用分窗算法：以 `min(70% × min(实际容量, 258k), 实际容量 − 输出/推理预留)` 为完整输入上限，再扣除完整请求开销及最多 2,048 token 的后续阶段余量。按资料顺序装窗，超长单片段在段落或句子边界拆分，保留原始证据 ID 和字符范围；打包后逐片段比对拼接正文与原文，防止静默丢尾。
- 每窗生成局部候选，跨窗按题目文本去重并尽量从不同窗口选题。每窗的请求、响应和实际用量仍完整记录。网关将供应商明确的上下文超限安全归类为 `CONTEXT_LIMIT`（不传出原始错误文本）；失败窗口遇到明确上下文超限或连续超时会单独缩小；已成功窗口的规划输出作为检查点保存，重试时复用。取消后也可使用检查点恢复。供应商不可用仍按原错误重试，不伪装成资料过长。
- 生成前展示模型容量来源、全文预计 token、净资料预算、预计窗口数与覆盖率；生成实录展示窗口编号、片段范围、预计与实际用量及去重情况。独立审核输入超过预算时改用引文附近的原文摘录，并明确记录；若仍超额会报错，不静默截断。
- 自动测试覆盖单窗、长片段完整拼接、双窗检查点、取消后恢复、上下文失败及连续超时后的局部缩窗、中英文混合估算、未知容量拒绝及取消 72k 字符截断。真实供应商是否接受约 180.6k 输入、不同模型的 tokenizer 偏差和 120 秒默认超时下的成功率，尚未经本轮验证；不应将本地估算当作供应商保证。

## 10. 大题数与窗口均衡（本轮）

- 单任务题数由原来的最多 20 道扩至最多 500 道。500 是防止误填造成高额调用和漫长任务的产品安全上限，不是模型单次输出上限。
- 资料窗口确定后，先给每个窗口分配一道局部候选，再轮流分配剩余配额。因此 10 道题、2 个窗口的正常规划目标是每窗 5 道；100 道、2 个窗口是每窗 50 道。预览会展示各窗题数配额。
- 初版曾规定每次规划最多 10 道，因此同一资料窗口可能被重复发送多次；这项主动拆批限制已在第 13 节所述改造中取消。供应商因输出过长拒绝时仍保留失败后对半拆分的恢复路径。
- 跨窗口汇总按**原始资料窗口**轮流取题，不把同一窗口的多次模型调用错当成多个窗口。去重导致不足时，再均匀地向各窗口补题，最多 3 轮；仍不足则明确报错，不悄悄少交题。
- 答案初版仍逐题生成，独立审核改为每次最多审核 10 道。答案与审核成功结果按任务配置、输入和提示词版本保存检查点；中断后重试可复用已验收结果。调用失败或被取消的部分不会当作成功复用。后续答案批处理改造见第 11 节。
- 本轮以本地自动测试验收拆批、窗口均衡与断点恢复；用户明确不要求真实模型验收，因此未调用真实供应商。真实题目质量、去重效果和供应商的实际输出限制仍需后续在用户环境观察。

## 11. 答案批处理与网络重试（后续改造）

- 答案阶段每次最多处理 5 道题，按照题目的证据 ID 只发送当前批所需的资料片段；输出 JSON 的 `ordinal` 必须与本批输入题号一一对应，允许模型乱序返回，但不接受重复或缺失题号。提示词版本更新为 `knowledge-studio.generate.v7`。
- 如果批量答案请求超出输入预算或输出结构失败，自动二分该批继续生成；若仅个别答案不符合 300 字、无清单等硬性要求，只单独重写不合格的题目，不重写同批合格答案。成功批次仍可作为重试检查点复用。
- 知识工坊的题目规划、答案生成和独立审核对超时、供应商暂不可用及限流错误最多进行 **5 次额外重试**（首次请求加重试共最多 6 次）。无效请求、鉴权失败和明确超预算不按网络错误反复重试。独立审核在重试耗尽后保留题目并标记人工复核。
- 本轮仍仅做本地自动测试、类型检查和构建；按用户此前要求，不调用真实模型验收。大批答案的真实质量、耗时和成本需在实际使用中观察。

## 12. 题面自包含与面试价值约束（后续改造）

- 出题提示词现为 `knowledge-studio.generate.v9`：明确候选人看不到参考资料，每题应能独立口头理解。通用题点明技术或概念；场景题交代业务或技术对象、必要条件和要判断的决策，但不泄露答案或编造背景。
- 题面自包含只是必要条件，不代表有面试价值。“必填房间数量缺失→询问房间数量”即使补充酒店背景也只是常识性动作，不应被改写成更长的题，而应舍弃。出题阶段优先选择能考察有依据的决策边界、取舍或机制的知识点。
- 独立审核增加两类判断：题面依赖隐含资料、指代不明或业务对象矛盾时标记 `needs_review`；答案只是重复题干给定条件、显而易见下一步，或资料不足以形成有价值问题时标记 `rejected`。已有服务端规则禁止将模型判为 `rejected` 的题直接人工批准。
- 这属于语义质量约束，自动测试只能验证提示词和调用协议已接入，不能证明模型必然遵守。当前审核会标记问题供人工修订，不会自动重写题面；可根据后续实际案例评估是否增设针对性重写步骤。

## 13. 取消出题阶段的单次 10 道限制

- 正常情况下，每个原始资料窗口按其全部题数配额调用一次问题规划模型。例如一个窗口分配 30 道即请求一次生成 30 道；两个窗口共分配 100 道则各请求一次、每次 50 道。不会为了遵守应用层 10 道上限而重复发送同一窗口资料。
- 跨窗口去重后的补题也不再人为限制每次最多 10 道。若模型明确返回输出长度不足或无效结构，才对失败请求的题数递归二分；上下文超限或连续超时仍按既有策略缩小失败窗口。模型自身的输出长度和上下文限制仍然有效。
- 下游答案每次最多 5 道、独立审核每次最多 10 道，本轮不改变。该改动只用本地自动测试验证调用次数与请求配额；大配额单次生成的真实质量由用户后续自行测试。
