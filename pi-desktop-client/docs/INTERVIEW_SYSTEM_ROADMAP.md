# 智能面试系统开发路线图

> 文档版本：1.2
> 对应客户端基线：0.6.0
> 最后更新：2026-09-21
> 状态：后续开发执行依据

平台级结构以 [Pi Desktop 多业务模块架构规划](./PRODUCT_MODULE_ARCHITECTURE.md) 为准。智能面试是业务模块之一，不再假定客户端以后只包含 Agent 和 Interview 两个系统。

## 1. 文档用途

本文档用于约束智能面试系统后续的产品范围、架构边界、开发顺序和验收标准。

后续开发遵循以下规则：

1. 优先完成一条可以真实使用、可以恢复、可以验证的纵向流程，不为了功能数量提前扩张。
2. 每个阶段必须完成数据库迁移、自动化测试和重启恢复验证后，才能进入下一阶段。
3. 面试业务不直接依赖 Pi 会话、Pi Memory 或 Agent 工作区状态。
4. SQLite 是正式业务数据来源，LanceDB 是可重建的检索索引。
5. 真实简历、候选人信息、岗位采集结果和面试记录不得提交 GitHub。

仓库上级目录中的《智能面试系统项目计划书》保留为早期产品构想。若其中的 Tauri、FastAPI、PostgreSQL、pgvector 等旧技术方案与本文档冲突，以本文档和当前代码为准。

## 2. 当前实施基线

### 2.1 已经完成

- 在现有 Electron + React 客户端中提供独立的“智能面试”模块入口。
- Agent 工作区和智能面试拥有不同的界面、状态 Store、IPC 命名空间和业务数据目录。
- 使用 SQLite 保存面试草稿、岗位描述、简历文本、岗位数据和采集历史。
- 使用 LanceDB 作为面试专属向量索引，已完成基础写入、检索和删除测试。
- 支持创建文本面试草稿，保存候选人、目标岗位、JD、简历、题数和能力维度。
- 支持阿里巴巴和字节跳动公开岗位的手动自动采集。
- 支持岗位标准化、去重更新、来源筛选、文本搜索和查看完整 JD。
- 支持从岗位库一键填充新面试草稿。
- 数据保存在 Electron `userData/interview` 目录，不进入项目仓库或普通 Pi 会话。
- 已建立独立 `InterviewModelProvider`，通过共享 Provider 配置直接调用模型，不创建 Pi Session。
- 已支持草稿经隐私确认后生成固定题目计划，并将计划、题目与安全调用摘要持久化到 Schema v3。
- 已提供独立面试会话页，展示准备进度、失败重试和可恢复的 Ready 状态；全部题目不会一次性发送给 Renderer。
- 可复用面试问答题库已完成离线浏览、收藏与本地练习闭环，详细边界见 [面试问答题库架构与迭代计划](./INTERVIEW_QUESTION_BANK_ARCHITECTURE.md)。

### 2.2 尚未完成

- 面试开始、作答、追问、结束和报告流程。
- 逐轮回答、评分、证据和报告的完整持久化用例。
- PDF、DOCX 简历导入与结构化解析。
- 知识文档入库、切分、Embedding 生成和混合检索。
- 岗位技能画像、简历技能画像和匹配分析。
- 动态追问、难度调整和不确定度判断。
- 训练建议、跨场次趋势、数据导出和完整数据删除。
- 岗位定时采集、岗位版本对比和过期识别。

## 3. 产品目标与边界

### 3.1 当前目标用户

- 准备互联网技术岗校招或社招的个人用户。
- 重点覆盖后端开发、AI 应用、算法和 Agent 开发岗位。
- 首版为本地单用户桌面应用，不建设账号、组织和多租户系统。

### 3.2 核心闭环

```text
选择岗位或粘贴 JD
  -> 导入或粘贴简历
  -> 生成岗位能力画像与面试计划
  -> 完成一场可中断恢复的文本面试
  -> 对每个结论给出回答证据和评分依据
  -> 生成能力缺口与下一步训练建议
  -> 再次面试并比较变化
```

### 3.3 暂不实施

- 自动投递、自动海投或代替用户联系招聘方。
- 绕过登录、验证码、访问限制或网站反爬机制。
- 视频表情、人格、情绪和录用概率判断。
- 多用户服务端、复杂权限、微服务和 Kubernetes。
- 在核心文本面试稳定前接入实时语音和视频。
- 将真实候选人数据同步到 GitHub 或默认上传云端。

## 4. 模块隔离原则

本节描述 Interview 自身边界；模块宿主、共享能力、目录结构和未来 Reading Assistant 的边界见《Pi Desktop 多业务模块架构规划》。

### 4.1 可以共享的基础设施

- Electron 窗口、菜单、主题、字体和外层布局。
- 通用日志、错误格式、时间、ID、文件选择器和安全存储。
- 中立的模型目录、Provider 凭据存储和网络客户端。
- 通用 SQLite 连接工具或迁移工具，但不能共用业务表。

### 4.2 不允许直接共享的业务状态

- Pi Session、Pi 会话树和聊天消息。
- Pi Memory 文件和普通会话摘要。
- Agent 当前工作目录、项目文件选择和 Git 状态。
- Agent 的排队消息、工具调用和上下文窗口。
- 面试问题、回答、评分、报告和候选人资料。

### 4.3 模型调用边界

面试模块必须通过独立端口调用模型，不直接调用 `PiSessionService`：

```ts
interface InterviewModelProvider {
  generateStructured<T>(request: InterviewModelRequest<T>): Promise<InterviewModelResult<T>>;
  streamText?(request: InterviewTextRequest): AsyncIterable<InterviewTextChunk>;
}

interface InterviewEmbeddingProvider {
  embed(request: InterviewEmbeddingRequest): Promise<number[][]>;
}
```

Provider 凭据和模型目录可以由公共基础设施提供，但以下内容必须由面试模块自行管理：

- Prompt 模板与版本。
- 面试上下文组装。
- Token 预算。
- 结构化输出 Schema。
- 重试与降级策略。
- 面试调用日志。
- 会话状态和恢复。

因此，后续优化 Pi 的上下文记忆、会话压缩或工具系统，不应改变面试结果和面试数据。

## 5. 目标架构

```text
Interview React UI
  -> Interview Store / Gateway
  -> interview:* IPC
  -> Interview Application Service
       |-> SQLite Repositories（正式数据）
       |-> Interview Model Provider（模型推理）
       |-> Interview Embedding Provider（向量生成）
       |-> LanceDB Index（可重建索引）
       |-> Document Parsers（PDF/DOCX/TXT）
       |-> Job Source Adapters（岗位采集）
```

建议逐步将 `src/main/interview` 从当前平铺结构整理为以下边界，不要求一次性重构：

```text
src/main/interview/
  domain/           # 状态、实体、规则，不依赖 Electron 和数据库
  application/      # 用例编排：准备、开始、回答、结束、报告
  infrastructure/   # SQLite、LanceDB、模型、文档解析、岗位采集
  ipc/              # 参数校验和 IPC 适配
```

迁移原则：只有在新增功能触及某个旧文件时才顺手迁移，不进行没有业务收益的大规模目录重写。

## 6. 面试状态机

继续使用当前状态枚举：

```text
draft
  -> preparing
  -> ready
  -> interviewing
  -> generating_report
  -> completed
```

状态规则：

- `draft`：允许修改 JD、简历、题数和能力维度。
- `preparing`：生成岗位画像、题目计划和评分量表，不接受作答。
- `ready`：计划已固化，可以开始或重新准备。
- `interviewing`：一次只存在一个待回答问题。
- `generating_report`：不再接受新回答，正在完成汇总评分。
- `completed`：正式记录只读；如需重新训练，创建新场次。

每次状态转换必须：

1. 在 SQLite 事务内写入。
2. 校验当前状态是否允许操作。
3. 支持重复请求幂等，避免双击产生两题或两份报告。
4. 失败时保存明确错误，但不得留下半写入状态。
5. 客户端重启后可以从数据库恢复。

## 7. 数据与存储设计

### 7.1 正式数据与索引

| 数据 | 存储位置 | 是否可重建 |
| --- | --- | --- |
| 面试配置、问题、回答、评分、报告 | SQLite | 否 |
| 岗位原文、简历文本、知识文档元数据 | SQLite | 否 |
| 原始 PDF/DOCX 文件 | `userData/interview/files` | 否 |
| 文档分块文本与来源定位 | SQLite | 否 |
| Embedding 向量 | LanceDB | 是 |
| 页面筛选、临时加载状态 | Renderer Store | 是 |

### 7.2 后续迁移规划

数据库继续使用显式递增 Schema 版本，每个版本必须提供旧库升级测试。

#### Schema v5：可复用面试问答题库

## 8. RAG 设计原则

### 8.1 首批知识来源

- 当前面试使用的岗位 JD。
- 当前面试使用的简历。
- 人工确认的技术题库和评分量表。
- 允许使用的官方文档或公开学习材料。
- 当前场次已经发生的问答，仅在该面试范围内检索。

### 8.2 入库流程

```text
原始文档
  -> 内容哈希与重复检测
  -> 文本清洗
  -> 按标题和语义段落切分
  -> 保存 chunk、页码、字符范围和来源
  -> 生成 Embedding
  -> 写入带模型版本的 LanceDB 表
```

### 8.3 检索流程

```text
结构化过滤
  + SQLite FTS 关键词召回
  + LanceDB 向量召回
  -> RRF 合并
  -> 来源、岗位、能力维度和时效过滤
  -> 必要时轻量重排
  -> 返回带 chunkId 的引用
```

禁止只把一段相似文本交给模型而不记录来源。问题、追问和评分引用必须保留 `documentId`、`chunkId` 和原文片段。

### 8.4 索引可重建

- 向量记录必须保存 Embedding 模型、维度和索引版本。
- 更换模型时创建新索引，不混用不同向量空间。
- LanceDB 损坏或被删除后，可以根据 SQLite 文档分块重新构建。
- 索引任务可以取消、重试，并在 UI 中显示状态。

## 9. 开发阶段

## 题库阶段 Q1：本地可复用问答题库（已完成）

目标：先完成不依赖模型和网络的题库浏览闭环，并为文件、网页导入及后续 RAG 选题建立稳定数据边界。

### 任务

- 增加 Schema v5、旧库升级测试和 FTS 搜索。
- 建立版本化内置题包，启动时通过统一导入接口幂等同步。
- 实现关键词、题型、难度、岗位、技能和收藏筛选。
- 实现分页列表、按需详情、答题思路、评分点、常见误区、追问与来源展示。
- 收藏状态持久化，题包升级不能覆盖用户状态。
- 为后续 PDF、DOCX、Markdown、TXT、网页和手工录入保留来源、解析器、定位及 import receipt。

### 验收标准

- 重启和重复同步不会生成重复题目。
- 列表不加载完整参考答案，详情按选中题目读取。
- 搜索、筛选和收藏完全离线可用。
- Schema v3 旧数据无损升级。
- 内置题包损坏时拒绝半量导入并给出明确错误。

详细设计与后续阶段见 [面试问答题库架构与迭代计划](./INTERVIEW_QUESTION_BANK_ARCHITECTURE.md)。

## 题库阶段 Q2：本地练习闭环（已完成）

目标：在不依赖模型和网络的前提下，让题库具备可恢复、可复盘、可追踪的真实练习入口。

### 任务

- 增加 Schema v6、v5 升级测试以及练习批次、题目快照、作答和进度表。
- 支持从单题或当前筛选结果开始练习，并固化题目顺序和版本。
- 支持草稿自动保存、提交、跳过、继续练习、主动结束与历史查看。
- 回答提交前隐藏参考框架和评分点，提交后再展示 rubric 供用户复盘。
- 保存自评、已覆盖评分点、备注、薄弱技能和待复习状态。
- 使用 operation ID、状态版本和草稿版本处理重复点击、重试和乱序保存。

### 验收标准

- 客户端关闭后可恢复唯一的进行中练习及最新草稿。
- 回答提交前，IPC 响应中不包含参考答案、rubric、常见误区或来源详情。
- 重复提交、自评、跳过和结束不会产生重复记录。
- 题库升级后，历史练习仍按创建时的题目版本显示。
- 新题包损坏不影响已存在练习的恢复和历史读取。
- 练习业务不创建 Pi Session，也不要求模型或网络可用。

## 阶段 1：打通完整文本面试（进行中）

目标：从现有草稿出发，完成一场可以中断恢复的 3～10 题文本面试。

### 任务

- 建立 `InterviewModelProvider` 和结构化输出校验。
- 增加 Schema v3 及升级测试。
- 根据 JD、简历和能力维度生成固定题目计划。
- 实现准备、开始、提交回答、下一题、提前结束和恢复用例。
- 增加独立“面试室”页面。
- 显示当前进度、题目、回答框、提交状态和结束确认。
- 保存每轮原始问题和原始回答，不依赖 Renderer 内存恢复。
- 模型失败时保留当前问题和用户答案，允许重试。

### 首版限制

- 先按固化题目计划顺序提问。
- 暂不进行动态追问和自动难度调整。
- 暂不显示参考答案和即时分数，避免干扰后续回答。
- 继续使用用户粘贴的纯文本简历。

### 验收标准

- 可以完成一场 5 题文本面试。
- 每次只能提交一次当前题答案。
- 回答后关闭并重启客户端，能够恢复到正确题目。
- 准备或模型调用失败不会破坏草稿。
- 不创建任何 Pi 普通会话。
- 数据库从 Schema v2 升级后旧岗位和旧草稿仍然存在。

## 阶段 2：证据化评分与报告

目标：完成“回答—评分项—原文证据—改进建议”的闭环。

### 任务

- 增加 Schema v8。
- 为每道题保存能力维度、评分量表和最低证据要求。
- 按正确性、完整性、证据性、表达结构进行逐题评分。
- 区分“回答错误”“回答不完整”“缺少证据”和“不足以判断”。
- 增加规则校验：分数范围、理由不能为空、引用必须存在。
- 生成能力维度汇总和最终报告。
- 报告支持展开查看原回答、评分理由和引用。
- 支持重新生成报告，但保留报告版本。

### 验收标准

- 报告中每个关键结论都可以定位到至少一条回答证据或明确标记“无充分证据”。
- 相同保存数据可以重新生成报告，不依赖聊天上下文。
- 修改模型或 Prompt 后不会覆盖旧报告。
- 模型返回非法结构时自动重试一次，仍失败则允许用户手动重试。

## 阶段 3：简历文件与结构化证据

目标：从“粘贴纯文本”升级为可复用、可校正的简历资料。

### 任务

- 增加 Schema v9。
- 支持 PDF、DOCX、TXT 导入。
- 保存文件哈希，防止重复导入。
- 提取教育、工作经历、项目、技能和成果指标。
- 所有结构化字段保留页码或字符范围。
- 提供解析结果确认与人工修改页面。
- 创建面试时选择已有简历，也可以使用临时粘贴文本。
- 提供删除简历及其索引、场次引用提示和隐私说明。

### 验收标准

- 支持常见文本型 PDF 和 DOCX。
- 解析失败时仍允许查看原文本并手动填写。
- AI 提取结果不会在用户确认前覆盖原文。
- 删除操作不会留下 LanceDB 孤立向量。

## 阶段 4：知识库与混合 RAG

目标：为出题和评分提供可追踪的专业知识来源。

### 任务

- 增加 Schema v10。
- 建立文档管理和索引任务页面。
- 支持 Markdown、TXT、PDF 和手动录入题目。
- 实现分块、Embedding、LanceDB 写入和索引重建。
- 实现 SQLite FTS + LanceDB + RRF 混合检索。
- 提供检索测试台，展示查询、过滤条件、排序和引用片段。
- 记录每次用于出题或评分的检索结果。
- 建立小型人工标注检索回归集。

### 验收标准

- 删除 LanceDB 后可以完整重建。
- 固定评估查询的相关内容能稳定进入 Top 5。
- 出题和评分保存实际使用的 chunk ID。
- 空检索、Embedding 失败和模型不可用都有明确降级行为。

## 阶段 5：岗位匹配与自适应追问

目标：让面试真正针对岗位和候选人的能力缺口动态变化。

### 任务

- 建立标准技能词典、别名和能力分类。
- 从 JD 提取带原文证据的岗位技能画像。

- 展示匹配项、缺口、证据不足项和用户修正入口。
- 根据回答完整度、证据和置信度决定追问、切换主题或提高难度。
- 设置单能力最大追问次数和总轮次上限。
- 保存每次决策的输入、理由和结果。

### 验收标准

- 匹配结论可以定位到 JD 和简历原文。
- 同一能力不会无限追问。
- 动态决策失败时回退到原固定题目计划。
- 用户可以查看系统为什么追问或切换主题。

## 阶段 6：岗位采集生产化

目标：把当前可用的手动采集升级为可维护、可观察的数据管线。

### 任务

- 为站点结构变化建立固定样本解析测试。
- 支持采集结果导出，但不默认提交仓库。

### 验收标准

- 岗位正文变化可以查看前后版本。
- 一个来源失败不会阻止另一个来源保存。
- 定时采集有频率上限、取消机制和清晰状态。

## 11. API 与事件命名约定

IPC 继续使用 `interview:` 前缀：

```text
interview:get-snapshot
interview:get
interview:create
interview:prepare
interview:start
interview:submit-answer
interview:finish
interview:get-report
interview:get-job-library
interview:collect-jobs
```

异步事件：

```text
interview:preparation-progress
interview:report-progress
interview:index-progress
interview:job-collection-progress
```

约定：

- Renderer 只通过 Gateway 调用 preload API。
- React 组件不得直接拼 IPC 名称。
- 主进程负责权限、参数、状态和路径校验。
- Service 不依赖 Electron 类型，便于单元测试。

## 12. 测试与质量门槛

### 12.1 每个阶段必须具备

- 领域规则单元测试。
- SQLite 新库创建测试。
- 上一版本数据库迁移测试。
- Service 成功路径和失败路径测试。
- IPC 参数校验测试或等价契约测试。
- 客户端重启恢复测试。
- TypeScript 检查、全量测试和生产构建。

### 12.2 禁止使用真实用户数据测试

- 测试姓名使用虚构值。
- 简历、回答和报告使用短小的合成文本。
- 岗位采集真实冒烟测试只能取少量公开数据，不写入仓库 fixture。
- 如果需要稳定的岗位 fixture，必须脱敏并缩减为最少字段。

### 12.3 性能基线

- 面试列表和详情读取不应依赖模型或网络。
- 普通数据库读取目标在 200ms 内完成。
- 长任务必须显示进度，超过 30 秒支持取消或安全离开页面。
- Renderer 不加载完整向量数据。
- 单次面试上下文必须有明确 Token 预算。

## 13. 隐私与安全

- API Key 不写入 SQLite、日志或导出文件。
- 在首次向外部模型发送简历前明确提示数据将发送给所选 Provider。
- 模型调用日志默认只保存哈希、用途、Token、耗时和错误摘要。
- 原始简历保存在面试数据目录，不放入当前项目工作区。
- 删除简历、面试或知识文档时同步清理关联向量。
- 打开外部岗位链接前只允许 `https` 和已知招聘站点。
- 岗位采集不登录、不处理验证码、不绕过访问限制。
- 导出数据由用户主动触发，并明确包含哪些敏感字段。

## 14. Git 与发布规则

应该提交：

- 源代码、Schema 迁移和测试。
- 合成的最小测试 fixture。
- Prompt 模板和结构化 Schema，但不得包含用户数据。
- 本路线图和必要的架构说明。

禁止提交：

- `interview.db`、`interview.db-wal`、`interview.db-shm`。
- LanceDB 数据目录。
- PDF/DOCX 简历和候选人信息。
- 真实面试回答和报告。
- API Key、Cookie、浏览器临时资料和采集缓存。

版本策略：

- 每个完成的阶段至少提升一个次版本，例如 `0.6.x -> 0.7.0`。
- 同一阶段的修复提升补丁版本。
- 数据库 Schema 版本与客户端版本独立递增。
- 发布前必须验证旧数据升级，不使用删除用户数据库作为修复方案。

## 15. 完成定义

一个任务只有同时满足以下条件才算完成：

1. 用户可见行为已经实现，而不只是创建接口或占位页面。
2. 正式数据已经持久化，重启后能够恢复。
3. 失败、取消、重复点击和非法状态有明确处理。
4. 没有跨越 Agent 与 Interview 的业务边界。
5. 新增数据库结构包含迁移与升级测试。
6. TypeScript、全量测试和生产构建通过。
7. 未生成或提交真实用户数据和运行时数据库。
8. 本文档中的阶段状态和关键决策同步更新。
